Seller cards for AI buying agents

AI agents now research and shortlist vendors before a human ever visits the site. A seller card is the structured fact sheet they read to decide whether Integris makes the list. Below: examples to model on, Integris's cards filled with what's already public, where the cards should live, and the form problem that stops agents at the finish line.

The discovery form problem Integris seller cards Where they live

Critical

Today, no AI buying agent can use the discovery form

Every page ends with "Book a discovery session." When a buyer's agent gets to that step, there is nothing it can read, fill in or hand back to the buyer. It drops Integris and moves to a vendor it can act on. See why and how to fix it with HubSpot →

What a seller card is

There isn't one ratified "seller card" standard yet. In practice, a seller card is the same fact sheet published in a few layers so every kind of agent can read it:

  1. A visible fact page, in plain HTML, that answers the questions agents shortlist on: who you serve, what's included, certifications, pricing model, onboarding time, support terms, proof and how to engage. The Integris AI Page example is the company-level version.
  2. Structured data (schema.org JSON-LD) on that page and on each service page, saying the same thing in machine-readable form. It must match the visible text; markup that claims more than the page creates conflicts agents notice.
  3. An /llms.txt entry that points AI systems straight to the cards.
  4. An action route an agent can actually use: a plain form, a scheduling link or a documented intake endpoint. Optionally, later, an A2A agent card (/.well-known/agent-card.json) if Integris runs its own qualifying agent.

What a card looks like to an agent

The Managed IT card as schema.org JSON-LD, embedded on /services/managed-it/. It reuses the Organization record Integris already publishes (https://integrisit.com/#organization). Bracketed values are the gaps to fill.

{
  "@context": "https://schema.org",
  "@type": "Service",
  "@id": "https://integrisit.com/services/managed-it/#service",
  "name": "Managed IT",
  "serviceType": "Managed IT services",
  "provider": { "@id": "https://integrisit.com/#organization" },
  "areaServed": ["US", "AU", "NZ", "PH"],
  "audience": { "@type": "BusinessAudience",
    "numberOfEmployees": { "@type": "QuantitativeValue",
      "minValue": "[GAP]", "maxValue": "[GAP]" } },
  "description": "Fully managed, strategic or co-managed IT with a 24/7/365 U.S.-based help desk, a written roadmap and a 12-month budget.",
  "hasOfferCatalog": { "@type": "OfferCatalog", "name": "Managed IT plans",
    "itemListElement": [
      { "@type": "Offer", "name": "Fully managed IT",
        "priceSpecification": { "@type": "UnitPriceSpecification",
          "priceCurrency": "USD", "price": "[GAP: starting price]",
          "unitText": "per user per month" } },
      { "@type": "Offer", "name": "Co-managed IT" },
      { "@type": "Offer", "name": "Strategic IT" } ] },
  "termsOfService": "[GAP: SLA page]",
  "potentialAction": {
    "@type": "ScheduleAction",
    "name": "Book a discovery session",
    "target": "[GAP: agent-usable booking URL]" }
}

Where seller cards should live

Agents find cards by following predictable paths from the site root. Here's the structure, with what exists today and what needs to be added.

integrisit.com/

├── robots.txt exists — allows all crawlers; also confirm Cloudflare isn't blocking AI search bots

├── llms.txt exists · fix — list /ai-info/ and every service card first

├── sitemap_index.xml exists — add the /ai-info/ pages

├── ai-info/ add — company card (the AI Page example) + Organization JSON-LD

│   ├── managed-it/ · core/ · cybersecurity/ · cloud/ · advisory/ add — one card per service

│   └── index.md optional — markdown copy of the company card, dated

├── services/<service>/ exists · add — visible "At a glance" card block + Service JSON-LD

├── contact/ exists · fix — agent-usable discovery route (see below)

├── trustcenter.integrisit.com exists — link from every card as the certification source

└── .well-known/agent-card.json later — only once Integris runs an agent that can answer and qualify

Two rules make the structure work:

  • One fact sheet, everywhere. The company card, each service card, the service pages, the structured data, Clutch and LinkedIn should all state the same numbers in the same words. Agents cross-check, and conflicts cost the shortlist.
  • Link it so agents trip over it. Put the cards first in /llms.txt, add a footer link such as "Information for AI assistants" on every page, and keep each card dated.

Integris's /llms.txt today

Integris already has an /llms.txt, generated by Yoast SEO. It's the first file many AI systems read, and it currently sends them to the wrong places:

  • The Contact entry is described as calling "Domain Computer Services," a legacy brand.
  • CORE, Cybersecurity and Managed Cloud all reuse the Managed IT description word for word.
  • Financial Institutions links to the removed /industries/community-banks/ URL.
  • A blog post entry, "Your IT help desk has a new job," links to firstfocus.com.au instead of integrisit.com.
  • The Syracuse location links to /locations/san-angelo-tx-copy/, a copied draft; only 5 of 18 offices are listed.
  • Missing: Pricing, Industries, Highly Regulated Industries, Leadership, Locations, Support and the Trust Center.

Yoast builds this file from page titles and meta descriptions, so most fixes are made in those fields. Yoast's settings can also choose which pages it includes.

Integris's structured data today

Every page carries an Organization/LocalBusiness record, which is a good foundation. It needs to match what the site says:

  • Hours are set to 9:00–5:00 daily, which contradicts "24/7/365." Add a 24/7 support ContactPoint.
  • areaServed is United States only.
  • Address misspells "New Jersery."
  • Employee count (501–1,000) and the headquarters address appear only here, not on any visible page.
  • There is no Service, Offer or ContactPoint markup, so agents can't read individual services as structured data.

The discovery form: why agents can't use it

1. The form isn't in the page

The Contact page's HTML has no form, no fields and no submit address. HubSpot draws the form afterward with JavaScript, inside an iframe from js.hsforms.net. Agents that read pages without running scripts see nothing; agents that do run scripts see a third-party frame.

2. reCAPTCHA blocks automated submission

The form loads Google reCAPTCHA Enterprise, which exists to stop non-humans. HubSpot's form submission API also lists an error for forms with reCAPTCHA enabled, so the same form can't simply be submitted from code.

3. No other route to book

There's no scheduling link on any page checked, and "Book a discovery session" buttons have no destination an AI can read. The only fallbacks are a phone number and sales@integrisit.com, neither described as a way to book.

4. Nothing says what happens next

The fields (name, business email, company, optional phone, "How did you hear about us?" and more) aren't described anywhere an agent can read, and there's no stated response time. An agent can't tell its buyer what to expect.

How to fix it with HubSpot

The goal isn't to let bots spam the CRM. It's to give an agent a legitimate route that ends with a real, consenting buyer. In order of effort:

  1. Describe the route in plain text (an hour). On Contact and every card, state: what the discovery session is, how long it takes, what you'll ask, the response time, and every way to start it — form, email, phone and booking link. Agents can relay all of this even before anything else changes.
  2. Publish a HubSpot Meetings link (a day). Create a public discovery-session scheduling page in HubSpot Meetings and link it as plain text on Contact, in /llms.txt and on the cards. An agent can hand the link to its buyer, and the buyer books in one click — a human completes it, so reCAPTCHA isn't an obstacle.
  3. Add a no-JavaScript fallback (a day). Behind the HubSpot embed, add a plain HTML fallback (a <noscript> block or visible text) that links to the meetings page and to a HubSpot-hosted form page. Readers that don't run scripts then still find a way in.
  4. Build an agent intake route (a sprint).
    • Create a separate, short HubSpot form for agent-assisted enquiries: name, business email, company, need, timeline, and a required "submitted on behalf of" field with consent text.
    • Put a small server-side endpoint in front of it — for example a WordPress REST route or a Cloudflare Worker on integrisit.com — that validates input, rate-limits, checks for spam and forwards to HubSpot's form submission API (api.hsforms.com/submissions/v3/integration/submit/…). The browser never sees HubSpot IDs, and the human form keeps its reCAPTCHA.
    • Document the endpoint's fields in plain text on /ai-info/ and in /llms.txt, and add it as the potentialAction target in the structured data.
  5. Confirm before sales follows up. Tag agent submissions in HubSpot (a hidden "source = AI agent" field) and route them to a workflow that emails the named buyer a confirmation link. Sales engages once the buyer confirms, so no lead is ever created without the buyer's consent.
  6. Test with real agents. Ask ChatGPT's agent mode, Perplexity Comet and Gemini in Chrome to "book a discovery session with Integris." Check that they find the route, and that submissions land in HubSpot with the right source.

Before building step 4: HubSpot labels the v3 form submission API "legacy" in its developer docs. Check the current submission endpoint and its rate limits with HubSpot first, and have marketing and legal sign off the consent wording.
